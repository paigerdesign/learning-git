Git cheat sheet

01

Repository

The project folder, tracked by Git and hosted on GitHub et al.

What it does

A repository is your project folder plus a hidden .git directory that stores every version of every file, along with who changed what and why. The local copy lives on your machine; a hosted copy on GitHub, GitLab, or Bitbucket (conventionally called origin) is the one your team shares.

git init
    git remote add origin https://github.com/you/my-project.git

Considerations

  • Add a .gitignore on day one so dependencies, build output, and .env files never get committed.
  • Never commit credentials. Deleting a secret in a later commit doesn't remove it from history, so rotate it instead.
  • Include a README and a LICENSE. A public repo without a license isn't open source by default.
  • One repo per deployable project is a sensible default. Monorepos are a deliberate choice that needs its own tooling.

02

Clone

Download a copy of the code to your machine.

What it does

git clone downloads the whole repository, including every file, commit, and branch, and sets up a remote named origin so you can pull and push later. You get the full history, not just the latest files.

git clone https://github.com/you/my-project.git
    cd my-project

Considerations

  • SSH or HTTPS: SSH keys save you from re-entering tokens, while HTTPS works through most corporate firewalls.
  • If you can't push to a project, fork it first and then clone your fork.
  • For very large repos, a shallow clone (--depth 1) or a partial clone (--filter=blob:none) saves time and disk space.
  • You only clone once. After that, run git pull to stay up to date.

03

Branch

A safe parallel timeline to the main codebase.

What it does

A branch is a lightweight, movable pointer to a commit. Creating one lets you build a feature or a fix in isolation while main stays stable. HEAD marks the branch you're currently working on, and it moves forward with each new commit.

git switch -c feature/login   # create and switch
    git branch                    # list branches

Considerations

  • Keep branches short-lived and focused on one change. Long-running branches drift and collect conflicts.
  • Use descriptive names such as feature/login or fix/42-mobile-tap.
  • Bring in changes from main regularly so your branch doesn't fall far behind.
  • Delete branches once they're merged to keep the list readable.

04

Commit

A snapshot + message describing your changes.

What it does

A commit records a snapshot of the files you've staged, together with an author, a timestamp, a message, and a unique hash. You decide what goes in by staging changes with git add, so one messy working folder can become several clean, focused commits.

git add login.html login.css
    git commit -m "Add login form"

Considerations

  • Commit small, logical units. Each commit should make sense on its own and ideally still build.
  • Write the subject line in the imperative ("Add login form", not "added stuff") and keep it around 50 characters.
  • Run git diff --staged before committing to catch files you didn't mean to include.
  • Commits stay local until you push, so you can safely amend or reword them before sharing.

05

Push / Pull

Upload to / download from the hosted repository.

What it does

git push uploads your local commits to the remote so teammates can see them. git pull downloads new commits from the remote and integrates them into your current branch. Under the hood, a pull is a git fetch followed by a merge or a rebase.

git push -u origin feature/login
    git pull

Considerations

  • Pull before you start work and again before you push, so conflicts stay small.
  • A rejected push means someone pushed first. Pull, resolve any conflicts, and push again.
  • Avoid --force on shared branches. If you really have to, use --force-with-lease, which refuses to overwrite work you haven't seen.
  • Run git config pull.rebase true if you prefer a linear history when pulling.

06

Diff

The visual difference between two versions of code from two different branches.

What it does

A diff shows exactly which lines were removed (−) and added (+) between two versions. Those versions can be two commits, two branches, or your working folder and the last commit. It's also what reviewers read in a pull request.

git diff                       # unstaged changes
    git diff --staged              # what you're about to commit
    git diff main...feature/login  # what the branch changed

Considerations

  • Run git diff before every commit. It catches leftover debug logs and stray edits.
  • Reformatting creates noisy diffs. Put formatting changes in their own commit, and use -w to ignore whitespace.
  • Three dots (main...feature) compares against the common ancestor, which shows only what the branch itself changed.
  • Use --word-diff when reviewing prose or long lines.

07

Merge

Combine a branch back into another branch.

What it does

Merging takes the commits from one branch and combines them into another. When both branches have moved on, Git creates a merge commit with two parents, which preserves the complete history of both timelines.

git switch main
    git merge feature/login

Considerations

  • Merge the latest main into your branch first, so any conflicts surface on your branch rather than on main.
  • If main hasn't moved, Git fast-forwards and no merge commit is created. Use --no-ff if you want one anyway.
  • GitHub offers merge commits, squash merging, and rebase merging. Teams usually standardize on one.
  • Run your tests after merging. A merge without conflicts can still produce broken code.

08

Rebase

Replay your commits on top of the latest main.

What it does

Rebasing replays your branch's commits one by one on top of the latest main, as if you had started your work from there. You end up with a straight, linear history. Each replayed commit is a brand-new commit with a new hash.

git switch feature/login
    git rebase main

Considerations

  • The golden rule: don't rebase commits other people have already pulled. Rewriting shared history causes serious confusion.
  • After rebasing a branch you've already pushed, you'll need git push --force-with-lease.
  • Conflicts are resolved one commit at a time. Use git rebase --continue to proceed, or --abort to back out.
  • git rebase -i lets you squash, reword, or reorder commits before you open a PR.

09

Merge conflict

Two changes touched the same lines; you choose.

What it does

A conflict happens when two branches change the same lines and Git can't tell which version to keep. Git pauses, marks the disputed region with <<<<<<<, =======, and >>>>>>>, and asks you to decide. You can keep one side, keep both, or write something new.

git status          # list conflicted files
    # edit the file and remove the markers
    git add style.css   # mark it resolved
    git commit

Considerations

  • Don't panic. git merge --abort or git rebase --abort puts everything back the way it was.
  • Delete every conflict marker. If you commit them, your code will break.
  • Make sure you understand both changes before you choose, and ask the other author if you're unsure.
  • Small branches that sync often run into fewer and smaller conflicts.

10

Pull Request (PR)

"Please review and merge my branch."

What it does

A pull request proposes merging your branch into another branch, usually main. It gathers the diff, the discussion, automated checks, and approvals in one place, so changes get reviewed before they land. GitLab calls the same thing a merge request.

git push -u origin feature/login
    gh pr create --base main --fill   # GitHub CLI

Considerations

  • Keep PRs small and focused. Reviewers catch far more in 200 lines than in 2,000.
  • Write a description that covers what changed, why, and how to test it. For UI changes, add screenshots.
  • Write "Fixes #42" in the description so the linked issue closes automatically when the PR merges.
  • Open a draft PR early if you want feedback before the work is finished.

11

Issue

A ticket: bug, feature, or task.

What it does

An issue is a ticket that tracks one unit of work, such as a bug, a feature request, or a task. It holds the description, the discussion, labels, and assignees, plus links to the pull requests that resolve it.

gh issue create --title "Login button does nothing on mobile" --label bug

Considerations

  • For bugs, include steps to reproduce, expected versus actual behavior, and the environment (browser, OS, version).
  • Search existing issues before filing so you don't create a duplicate.
  • Apply labels and assignees consistently so the backlog stays searchable.
  • Issue templates and forms prompt reporters for the details you need.
